prolog userworld: giving an ai conversation a real memory

i built a small proof of concept around a very old ai habit: write the facts down, write the rules down, and make the machine show its work before it answers.

published july 2026 python + swi-prolog debian proot on android apache-2.0
why this exists what prolog is how userworld works use cases memory harnesses benchmark thesis seed sources

why this exists

my first serious ai work was prolog-era, rule-based expert-system work. in 2008 i published an itb thesis on a computer program for expert-system-based environmental impact analysis for cement industry projects. the archive still has the old title, the pdf chapters, and the keywords: amdal, program komputer, sistem pakar.

that ai scene was small. we wrote rules, asked structured questions, and made the program walk through a domain the way a human expert might. after that came big data, cloud, blockchain, crypto, and the current language-model wave. the current wave has a different failure mode: the model can produce fluent paragraphs while losing track of where a fact came from, which topic it belongs to, and whether a newer statement has replaced it.

prolog userworld is my attempt to reuse that expert-system discipline for long-running llm conversations. the name is literal. a userworld is the world the system has built around one user: projects, people, preferences, procedures, active topics, stale facts, and unfinished threads.

i do not want memory to mean "dump the chat log into the prompt" or "search for similar text and hope." i want rules, provenance, contradiction handling, scope, and an explanation for each piece of context.

what prolog is, in normal human language

prolog is a programming language from the old ai world. most languages tell the computer exactly what to do step by step. prolog lets you describe facts and rules, then ask questions.

instead of writing "loop through this list and check every item", you can write a rule like this: "a memory is relevant if it belongs to the current topic, or if it is global and matches the person we are discussing, and it has not been revoked or superseded." then prolog searches for the answers.

% tiny prolog example
person(danny).
project(danny, glasses).
project(danny, prolog_userworld).

same_person(X, Y) :-
    person(X),
    person(Y),
    X = Y.

% query:
% ?- project(danny, What).
% What = glasses ;
% What = prolog_userworld.

that is why prolog showed up in expert systems, planning, legal-ish rules, medical triage, and symbolic reasoning. bad facts still produce bad answers. the advantage is that the mistake is often visible in the facts or the rule that fired.

the architecture

the prototype is small. python receives the user turn, extracts candidate memories, then asks swi-prolog to make the actual decisions. prolog is the control plane. python is the plumbing.

the system stores:

  • episodic memory: what happened in the conversation.
  • semantic memory: facts about people, projects, preferences, and relationships.
  • procedural memory: reusable workflows, triggers, steps, and completion conditions.
  • working memory: the active topic, goal, entities, and constraints.
  • temporal state: when a fact became valid, expired, or got superseded.
  • provenance: where a memory came from.
  • epistemic status: explicit user statement, observation, inference, hypothesis, or suggestion.

the memory file is an append-only event log. old facts are not deleted when they become wrong. they are superseded. that lets the system answer a question normal chat memory usually cannot answer: "what did i believe at the time?"

python -m userworld chat
python -m userworld demo
python -m userworld eval
python -m userworld inspect
python -m userworld explain --text "back to danny's glasses" --entity danny --entity glasses
python -m userworld reset

the prolog side has fixed predicates for the dangerous decisions. untrusted model output never becomes an arbitrary prolog goal. it becomes validated data.

% simplified from the prototype
memory_active(Id) :-
    memory(Id, _, _, _, _, _, _, _, _, _, _, ValidUntil, SupersededBy, Revoked, _, _, _),
    Revoked \== true,
    noneish(SupersededBy),
    noneish(ValidUntil).

memory_visible_for_topic(Id, CurrentTopic, QueryEntities, QueryText, include, Reason) :-
    memory(Id, _, Subject, Predicate, Object, Topic, Scope, _, _, _, _, _, _, _, _, _, Text),
    memory_active(Id),
    Scope == topic,
    Topic == CurrentTopic,
    ( token_overlap(QueryText, Text)
    ; token_overlap(QueryText, Subject)
    ; token_overlap(QueryText, Predicate)
    ; token_overlap(QueryText, Object)
    ),
    Reason = 'topic-local memory belongs to the current topic'.

six use cases

the demo uses a weird conversation because weird conversations expose memory bugs quickly. it starts with infrared anti-photography glasses, switches into llm memory architecture, learns a research workflow, then returns to the glasses and changes a technical fact.

1. learn topic-scoped facts

danny is building infrared anti-photography glasses. the system records the project and the technical details as topic-local facts, not universal truth.

2. switch topics without losing identity

when the conversation moves to prolog memory architecture, danny remains the same person, but the infrared details do not pollute the new prompt.

3. learn a reusable workflow

the user can teach a procedure: collect primary sources, build a comparison matrix, run evaluation, document limitations. later, a research request triggers that workflow.

4. resume an old topic and supersede a fact

"back to danny's glasses" resumes the glasses topic. the old 940nm led fact is not erased, but the new 850nm fact supersedes it.

5. inspect and explain

the system can report its current counts, active topic, selected memories, and excluded memories with reasons. this is the part i care about most: the explanation belongs in normal use, not hidden in a log file.

6. compare against simple memory baselines

the benchmark compares full history, last-n turns, lexical retrieval, and prolog userworld. this is a synthetic benchmark, so i treat it as a smoke test for the rule set.

how it compares with other memory harnesses

there is already a wave of memory systems for agents. prolog userworld is not trying to replace all of them. it handles a narrower problem: explicit rules over a personal memory file that changes over time.

approach what it is good at where prolog userworld is different
full chat history simple, complete, no retrieval logic. bloats the prompt and drags irrelevant old topics into new work.
sliding window cheap and predictable. forgets old but important facts, especially after interruptions.
vector search / bm25 good at semantic similarity and fast retrieval. similar text can still be out of date, out of scope, or based on the wrong authority.
langgraph memory short-term state via checkpoints and long-term stores across sessions. userworld puts declarative rules in charge of context inclusion and exclusion.
memgpt / letta stateful agents that manage growing context and persistent memory. userworld is smaller and stricter: prolog predicates decide mutation, routing, and selection.
mem0 developer-friendly persistent memory layer for apps and agents. userworld is less productized. its bet is proof traces and contradiction rules.
zep / graphiti temporal knowledge graphs with evolving entities and relationships. userworld keeps the time-aware instinct, then writes the control rules in prolog.

the closest cousin is probably a temporal knowledge graph plus a rule engine. in prolog userworld, the rule engine is the main memory surface.

the benchmark, with the caveats up front

the current benchmark has 30 synthetic scenarios covering abrupt topic switches, nested digressions, resuming old topics, shared entities, ambiguous references, contradictions, superseded facts, temporary instructions, procedural recall, multi-step goals, revoked information, topic-local facts, and globally available facts.

the numbers are clean because the scenarios test the rule semantics directly. they show that the program follows the rules that were written for it. they do not show that the rules are complete, or that this will beat embeddings on a messy external dataset. the next step is a held-out benchmark with conversations written by someone else.

why this may become a thesis

the thesis question is plain: can a symbolic memory layer make long-running ai conversations easier to audit?

to answer that properly, i would compare behavior, not only retrieval scores. does the system avoid leaking stale topic details? does it preserve provenance? can a human inspect why a memory was selected? can it manage durable procedures without turning guesses into facts?

this prototype runs on a phone, inside debian proot, with python and swi-prolog. i like that constraint. it keeps the architecture small enough to read.

next experiment

replace the deterministic extractor with model-assisted extraction, while still labeling each memory as user statement, observation, inference, hypothesis, or suggestion.

next benchmark

build a messy, human-authored set of conversations with topic switches, reversals, privacy traps, and long interruptions.

next architecture

try a resident prolog process so selection latency is no longer dominated by subprocess startup.

next paper

frame prolog userworld as executable declarative memory: different from retrieval, summarization, or a one-off tool call.

try it

the code is public. it installs with a normal python virtual environment and swi-prolog. the offline demo and benchmark do not need an api key.

git clone https://github.com/Decentricity/prolog-userworld.git
cd prolog-userworld
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -e ".[dev]"
python -m userworld demo
python -m userworld eval
