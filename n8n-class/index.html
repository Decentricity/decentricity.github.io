    Two-day practical workbook

    n8n AI Workflow Automation

    Build useful workflows around Microsoft 365 and Azure, then learn how to reuse, version, promote, monitor, and repair them.

    Start day one Jump to day two

    Course map

    This class assumes the organization is procuring its own corporate n8n instance. We use a temporary NobleProg training instance for exercises; initial installation and server administration are outside the hands-on path. Your trainer will provide the training URL, access instructions, and approved sandbox credentials. Do not connect production tenants or put real company data in the training instance.

    Day one: workflow fundamentals, Microsoft authentication and actions, Azure OpenAI, AI decisions, and failure handling. Day two: a Microsoft operations use case, community resources, JavaScript extensions, Git/CI/CD, environment promotion, and monitoring.

    Working example: an operations request arrives, n8n classifies and summarizes it, routes it to a human, records a result, and reports failures. The exercises build toward this one scenario, so you can reuse work from the previous lab.

    Before class: access and lab data

    The training environment may run on a NobleProg server or Ddesktop. Hosting is to be confirmed before class. Participants need a browser, an individual training login, and permission to create workflows. The trainer should test outbound access to Microsoft services, callbacks required for OAuth, and the Azure OpenAI endpoint ahead of time.

    • Prepare a training-only Microsoft tenant or approved test accounts with a Teams channel, Outlook mailbox, SharePoint list, and, if available, a Dataverse test table. Use least-privilege app permissions approved by the tenant admin.
    • Prepare a sandbox Azure OpenAI deployment and connection details if live AI calls are planned. An Azure AI Search index, Azure Functions endpoint, Power BI workspace, and Power Apps test app are optional extensions; verify availability and access before committing to live demos.
    • If tenant access is unavailable, use the supplied example request below with Manual Trigger and Set/Edit Fields. Exercise routing, logging, and recovery with test records; the Microsoft connection steps then become trainer walkthroughs.
    • Agree on where learners may store workflow JSON and whether a private corporate Azure DevOps repository is accessible. Never commit secrets, live payloads, or production identifiers.

    Day one: Microsoft-connected AI workflows

    Lab 1 — Build a first n8n workflow

    Goal: Understand triggers, nodes, items, expressions, executions, and where an AI step belongs. AI is useful for interpreting unstructured requests; deterministic routing and approvals still belong in explicit workflow logic.

    1. Open the provided training instance and create D1-01 Operations request.
    2. Add Manual Trigger, then Edit Fields (Set) with the sample request. Run each node and inspect its JSON output.
    3. Add an IF or Switch node. Route a request with a missing subject to an invalid-input branch; route a valid request to a processing branch.
    4. Add a clear status and timestamp to each branch using Edit Fields. Re-run with both valid and invalid input and inspect the execution history.

    Done when: both test cases have visible, different results and you can identify which node produced each field.

    Lab 2 — Microsoft services and secure connections

    Goal: Replace sample input with a Microsoft business event and make an approved Microsoft action. Use native nodes when the required operation is available; use authenticated HTTP Request against Microsoft Graph or the service API for gaps. Check the installed n8n version and permissions before choosing an operation.

    1. Choose one sandbox intake source: an Outlook message, a SharePoint list item, or a Teams event if the training tenant supports its trigger. Otherwise retain Manual Trigger and sample input.
    2. Create or select the appropriate Microsoft credential using the tenant-approved OAuth configuration. Record required scopes and admin consent with the trainer; do not paste access tokens into node parameters or workflow JSON.
    3. Normalize the incoming record to requestId, subject, description, source, and submittedAt. Test with a sandbox record.
    4. Choose one output: post a status message in a sandbox Teams channel, draft or send an Outlook reply to a test mailbox, or update a SharePoint list item. Verify exactly one action for one request.

    Integration map: Teams, Outlook, and SharePoint are the core practice services. Dataverse is a possible case record store; Power Apps can submit a request through an approved API or webhook; Power BI can consume a cleaned output through an approved interface. Azure Functions and other APIs fit through HTTP Request. We will discuss each connection pattern without assuming every tenant or n8n edition has every node and operation.

    Done when: a test request enters the workflow and produces an action in a permitted Microsoft sandbox. If live access is blocked, show the mapped payload and explain the missing permission or endpoint.

    Lab 3 — Azure OpenAI classification and response

    Goal: Add a bounded AI decision to the same workflow. Use the Azure OpenAI Chat Model with the appropriate AI node when the training deployment is available; the exact node settings depend on the deployed n8n and Azure versions. Ask for a structured result and validate it before any external action.

    1. Provide the request subject and description to an AI step. Ask it to return category (incident, service_request, or other), urgency (low, medium, or high), summary, and reason. Treat the result as untrusted data.
    2. Parse the response and use IF/Switch to accept only allowed values. On malformed output or uncertain classification, send the request to a human review branch.
    3. For a high-urgency test request, generate a concise Teams notification or Outlook draft. Keep the request ID in the message and require human confirmation before a consequential action.
    4. Run three cases: routine request, urgent incident, and ambiguous request. Compare the model's decision to the explicit validation and routing logic.

    Optional retrieval: retrieve a short approved troubleshooting excerpt from Azure AI Search or another authorized knowledge source, pass it to the model, and require the response to cite its source. Skip retrieval if an index has not been prepared.

    Done when: the workflow accepts a valid AI result, rejects an invalid one, and places an ambiguous case into review.

    Lab 4 — Errors, retries, and safe notifications

    Goal: Make failures visible without silently duplicating updates or messages.

    1. Deliberately fail a sandbox API action. Inspect the failed execution and identify the node, request ID, and error response.
    2. Choose how to handle temporary failures: retry with limits for an idempotent operation, or route the error for review. Discuss how to avoid duplicate Teams posts or repeated writes on retry.
    3. Create a separate workflow beginning with Error Trigger and attach it as the main workflow's error workflow. Send a short alert to a test Teams channel or trainer-designated mailbox. Include workflow name, execution link, and request ID if available; omit sensitive payloads.
    4. Run the failure case again. Confirm an alert is raised and the execution can be traced to its failed step.

    Done when: the failure is visible in Executions and produces one actionable alert.

    Day two: reuse, DevOps, and operations

    Lab 5 — End-to-end Microsoft operations intake

    Goal: Combine the day-one pieces into an office workflow that can be demonstrated to an operations team.

    1. Receive a test request from Outlook, SharePoint, or the sample Manual Trigger. Normalize fields and reject incomplete submissions.
    2. Classify and summarize with Azure OpenAI if available. Add an explicit human-review branch for uncertain or high-impact cases.
    3. Create or update a sandbox SharePoint or Dataverse record, notify a Teams channel, and draft an Outlook response. If a Power Apps front end or Power BI reporting destination exists, map where it sends or receives the same request and status fields.
    4. Use a child workflow for a reusable status format or audit event. Add a correlation ID, timestamps, and a clear success/failure outcome.
    5. Test a normal request, a missing-field request, and a simulated downstream outage. Confirm the record and notification match the chosen branch.

    Done when: you can demonstrate the three outcomes and identify where a human takes over.

    Lab 6 — Learn from the n8n community

    Goal: Find and adapt an existing workflow or node instead of starting from a blank canvas. A workflow template is importable workflow logic; a community node is installed code and needs a separate approval decision.

    1. Search the n8n workflow library for Teams, Outlook, SharePoint, or an Azure use case. Pick one candidate and inspect its trigger, credentials, external calls, data handling, and maintenance date.
    2. Import or copy the candidate into the training instance, then replace example credentials, endpoints, and recipients with approved sandbox values. Remove any unnecessary third-party step.
    3. Compare its behavior against your intake workflow using the three test cases. Keep only the parts that improve the workflow and document changes.
    4. Find a relevant community node in the n8n UI or package registry. Review publisher, source, permissions, release history, and whether an existing built-in node or HTTP Request already covers the need. Install only if the trainer and instance administrator approve it; otherwise perform a review exercise.

    Done when: you can explain why you would adopt, adapt, or reject a published workflow and a community node.

    Lab 7 — Extend with JavaScript or an API

    Goal: Use a small Code node for a transformation that is awkward in mappings; use HTTP Request for an approved Azure Function or service API. Custom node development is a design discussion, not a requirement for this two-day course.

    1. Add a Code node that normalizes a test urgency label and preserves requestId. Check behavior with an unexpected label and missing ID.
    2. Discuss when this logic belongs in Edit Fields, a Code node, a reusable child workflow, an Azure Function, or a custom n8n node.
    3. If a test Azure Function is provided, call it through an authenticated HTTP Request and inspect its response and failure behavior. Do not call a production endpoint from the lab.
    // Code node: Run Once for All Items
return $input.all().map(item => {
  const requestId = String(item.json.requestId || '').trim();
  if (!requestId) throw new Error('Missing requestId');
  const allowed = new Set(['low', 'medium', 'high']);
  const value = String(item.json.urgency || '').toLowerCase().trim();
  return { json: { ...item.json, requestId, urgency: allowed.has(value) ? value : 'review' } };
});

    Done when: a valid urgency passes through, an unknown urgency becomes review, and a missing request ID fails visibly.

    Lab 8 — Version, promote, and monitor

    Goal: Define a credible path from a sandbox workflow to development, test, and production instances with different databases and service connections.

    1. Export the completed workflow JSON. Review it before committing: exported files can include credential names and IDs, node parameters, URLs, and sample data. Remove sensitive or environment-specific values according to company policy.
    2. Commit the reviewed JSON to a private corporate Azure DevOps repository. In a pull request, check naming, test cases, dependency/node versions, intended recipients, and rollback steps. Never store actual credential secrets in Git.
    3. Map development, test, and production to separate n8n instances and separate Microsoft credentials, Azure deployments, database connections, and webhook URLs. Test each environment with its own fixture before publishing or activating the workflow.
    4. Discuss two promotion routes: (a) manual/API-based export, review, and import using approved pipeline tooling; (b) n8n's built-in Git source control and environments if the corporate license and admin permissions include that feature. The built-in option is plan-dependent and needs separate instance configuration; do not assume it exists in the temporary training instance.
    5. Inspect the Executions view for successful, failed, and waiting runs. Drill into a failed step, decide whether retry is safe, and check the error workflow alert. Define an owner, alert destination, retention policy, and response procedure for a production workflow.

    Release drill: change a test routing rule, export and review the JSON diff, run the three regression cases in test, then write a short promotion and rollback note. Promotion to the client's real production instance is a design exercise only.

    Done when: you have a reviewed workflow artifact, environment mapping, test evidence, and an incident response path.

    Reference notes

    For current node operations and tenant setup, use the Microsoft credential guide, Teams node, Outlook node, and Azure OpenAI Chat Model documentation. The available actions and authentication prompts may differ by version and tenant policy.

    The source control and environments tutorial describes the licensed built-in promotion route; the Executions guide covers run history and retries. Review the workflow export/import guidance and community node guidance before sharing or installing anything.

    Class examples use synthetic operations data. Adapt permissions, retention, approvals, and deployment steps to the client's corporate policies.
