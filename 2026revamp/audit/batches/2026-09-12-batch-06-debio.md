# Audit batch 06 — DeBio Network component audit

DeBio is one serious multi-repository system. These repositories should **not** become separate public project cards. The correct public entity is **DeBio Network**, with the repos below grouped as implementation evidence/components and with upstream/reference repos clearly separated.

## Core DeBio system repositories

### `debionetwork/debio-node` — core blockchain component
README identifies **DeBio Node / Decentralized Sovereign Biomed**, an anonymous-first platform for medical and bioinformatics data using blockchain as an immutable transaction ledger. It is a Substrate-based chain/node with local-chain and Docker workflows.

### `debionetwork/debio-backend` — backend component
Nest.js/Node backend for DeBio Network. README explicitly identifies it as the network backend and provides production/development/Docker workflows.

### `debionetwork/debio-background-worker` — chain event/indexing/application worker
README is unusually detailed: the worker synchronizes historical and current Substrate events and handles Labs, Orders, Services, Genetic Testing/Data Staking, Service Requests and Certifications. This is substantive application infrastructure, not a generic worker template.

### `debionetwork/debio-frontend` — dashboard UI
Vue 2 frontend dashboard for the DeBio platform.

### `debionetwork/debio-customer-ui` — customer UI
Dedicated Vue customer-facing application.

### `debionetwork/debio-lab-ui` — laboratory UI
Dedicated Vue lab-facing application.

### `debionetwork/debio-genetic-analyst-ui` — genetic analyst UI
Dedicated Vue interface for genetic analysts.

### `debionetwork/debio-infrastructure` — deployment/infrastructure component
README identifies it as **DeBio Network Infrastructure**; limited prose, but clearly project-owned operational infrastructure.

### `debionetwork/debio-smart-contracts` — EVM/escrow/service-request component
README documents real business logic: partial/full escrow payment, order fulfilment/refunds, request-service staking, curated labs, service offers, customer processing, unstaking and bridging parameters between EVM contracts and the DeBio Substrate order/service model. This is core product logic, not a demo contract.

### `debionetwork/debio-charts` — Helm/deployment packaging
README documents DeBio Helm charts and the `debio-app-deployer` chart/repository usage. Supporting infrastructure.

### `debionetwork/api-wrapper` — DeBio JS/API package
README brands the package as `@debionetwork/polkadot-provider`. This appears to be a project-specific provider/API wrapper; supporting library.

### `debionetwork/polkadot-provider` — DeBio JS/provider package
README is identical DeBio-branded `@debionetwork/polkadot-provider` material. Supporting application library; likely related/duplicate lineage with `api-wrapper`, not a separate public project.

### `debionetwork/ui-components` — shared UI library
README explicitly says the DeBio team jointly developed the Vue component collection so DeBio applications do not recreate components repeatedly. Supporting first-party package.

### `debionetwork/ui-icons` — shared icon package
DeBio-branded shared package; supporting UI library.

### `debionetwork/pinata-ipfs` — IPFS integration package
DeBio-branded `@debionetwork/pinata-ipfs`; supporting storage/integration library.

### `debionetwork/ocean-js-test-scripts` — Ocean Protocol integration experiment/support
README explicitly says these are test scripts for publishing biomedical datasets to **DeBio's self-hosted Ocean Protocol node**, based on Ocean.js tutorials. This is project-specific R&D/integration support rather than a standalone project.

### `debionetwork/ipyrad-dockerfile` — bioinformatics deployment support
README says “Miniconda3 Ipyrad Dockerfile Image.” Supporting packaging for the upstream ipyrad tooling used in DeBio bioinformatics workflows.

### `debionetwork/vcf2pca` — project-specific bioinformatics compute wrapper
README is only “VCF PCA,” so source was inspected. `pca.py` is an Ocean compute-job style wrapper: it reads DIDs/DDOs and input paths from the compute environment, uses `ipyrad.analysis.pca`, renders the PCA result with Toyplot, and writes output. Treat as DeBio bioinformatics/Ocean compute support, not a standalone product.

## DeBio indexing/adapted components

### `debionetwork/debio-subql` — adapted SubQuery indexer component
README is still the generic SubQuery starter README, but `project.yaml` is DeBio-specific: name `subql-debionetwork`, DeBio Octopus mainnet WebSocket endpoint, DeBio genesis hash and Substrate block handler. Therefore this is an adapted indexing component despite stale starter documentation. Do not classify as pure upstream or as its own project.

## Upstream / third-party repositories living in the org

### `debionetwork/ipyrad` — upstream-reference
`README.rst` is the standard ipyrad project README, cites Deren Eaton & Isaac Overcast and the Bioinformatics paper. This is upstream bioinformatics software, not a DeBio-authored project.

### `debionetwork/vcf2csv` — upstream/reference, misleading repo name
No Markdown README; `README.txt` was inspected. It is the standard **VCF2PopTree** documentation, explicitly linking `github.com/sansubs/vcf2pop` and citing Subramanian, Ramasamy & Chen (2019). Despite the repo name, it is not evidence of a DeBio-authored VCF-to-CSV project.

### `debionetwork/vcf2pop` — upstream VCF2PopTree copy
Root includes the same `README.txt` blob as `vcf2csv`, plus a large client-side `index.html` and test VCFs. Treat as upstream/reference unless commit provenance later demonstrates material DeBio changes.

### `debionetwork/nestjs-gcloud-storage` — upstream/third-party library
README installs and imports `@aginix/nestjs-gcloud-storage` and attributes package identity to Aginix. Keep out of DeBio-authored component claims unless a diff demonstrates a substantive fork.

### `debionetwork/polkadot-js-apps` — upstream Polkadot UI
README is the standard `@polkadot/apps` portal and clone instructions point to `polkadot-js/apps`. Upstream/reference; not DeBio-authored.

### `debionetwork/sphere` — upstream DIYbiosphere
README explicitly identifies **DIYbiosphere**, links `DIYbiosphere/sphere` as the raw-file repository, and describes the global DIYbio directory/wiki project. Upstream/reference; not a DeBio component despite living in the org.

### `debionetwork/debio-web-info` — third-party coming-soon template / low-value support
README is the generic “Coming Soon” single-file HTML template and credits `dr5hn`. It may have been used for a DeBio web surface but is not substantive project evidence.

## First-party reusable package

### `debionetwork/nestjs-gcloud-secret-manager` — DeBio-authored reusable package
README identifies `@debionetwork/nestjs-gcloud-secret-manager`, installs it from npm, describes it as Google Cloud Secret Manager for Nest.js and gives MIT © DeBio Network. First-party reusable package; supporting library rather than project card.

## DeBio project-level normalization

Public project entity should be **DeBio Network** with a summary grounded in the actual core repositories: decentralized, anonymous-first medical/bioinformatics platform with a Substrate blockchain, application backend and event worker, specialized customer/lab/genetic-analyst UIs, EVM escrow/service-request smart contracts, deployment infrastructure and bioinformatics/Ocean integration work.

Do **not** describe every org repository as first-party. Explicitly exclude or label upstream copies such as ipyrad, Polkadot.js Apps, DIYbiosphere Sphere, VCF2PopTree and Aginix storage.

The repo corpus supports calling DeBio a substantial multi-surface system. It does not support pretending every target architecture idea or every org-hosted dependency was original DeBio code.
